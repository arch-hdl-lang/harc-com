# split-emit benchmark

Measures TB-IR split C++ emission (`--codegen tbir --cpp-split tests`) —
the frontend phase that harc#538 targets. Everything here runs under
`--emit-only`, so no Verilator is required.

```sh
cargo build --release
bench/split_emit/run_bench.sh                 # defaults: 352 tests, group 32, 3 reps
bench/split_emit/run_bench.sh /tmp/bench 16 5 # custom workdir / group size / reps
```

`gen_suite.py` writes a synthetic suite plus a trivial DUT. The production
suite that motivated the issue is proprietary and does not lower through
TB-IR yet (a passive composite-component gap, tracked separately), so the
generator reproduces the shape that matters instead: a double-digit shard
count, test bodies big enough that emitting a shard is real work, and
suite-global scaffolding (constrained transaction records plus a
`randomize` site per test) that exercises the solver problem table and
randomize snippets reused across shards.

Not wired into CI — it takes minutes and writes hundreds of MB.

## What to read

`harc` prints each frontend phase, so a slow run can be attributed
without reaching for a profiler:

```
TBIR parse: 7.4s | merge: 0.1s
TBIR lower: 3.2s | verify: 0.4s
TBIR split plan: 352 tests, 11 shards, group size 32, emit jobs 4, planned in 0.5s
TBIR shard 3/11: 32 tests, 31.7 MB, 0.3s, emitted
TBIR split emit: 11/11 shards, 348.6 MB, 0.8s
```

These are one representative run, not the medians tabulated below, so
they will not sum to any figure in this file. They cover everything
between reading the sources and the last shard hitting disk. What they do
*not* cover is process startup and teardown — dropping the AST and the
lowered program at exit — which is the largest unprinted contributor and
was measured at several seconds on this suite.

The final rerun in the script re-emits an unchanged suite. Every shard
then reports `reused`, so `write_if_changed` reads and compares but never
writes — the difference between that number and the clean-run emit time is
the write I/O.

## Reference measurement

4-core container, Linux 6.18, release build, 352 tests / 11 shards at
group size 32, 348.6 MB of generated C++.

Shard I/O runs on the worker that produced the shard. It used to run on a
single receiving thread, which serialized every shard's `write_if_changed`
— both the compare-read and the write — and put a ceiling on
`--emit-jobs`. Interleaved A/B against the previous implementation on a
shared 4-core host, 3-5 reps per cell, medians with observed ranges:

| jobs | I/O on receiver | I/O on worker |
|---|---|---|
| 1 | 2.0 s (1.8-2.1) | 1.9 s (1.7-2.1) |
| 2 | 1.3 s (1.2-1.4) | 1.1 s (1.1-1.2) |
| 4 | 1.2 s (1.1-1.2) | **0.7 s** (0.7-0.8) |

So ~1.7× on the emit phase at `--emit-jobs 4`, and speedup over serial
goes from ~1.7× to ~2.7×. Generated bytes are identical across every cell
and against the pre-change binary.

Treat the absolute seconds as soft: this host is shared and lowering
alone swung 8-13 s between runs. Only interleaved comparisons are
meaningful, and the ratios were stable across reps where the absolutes
were not. An earlier revision of this table reported 1.4 s for the
receiver-side `--emit-jobs 4` cell, which did not survive re-measurement —
non-interleaved timings on this host are not trustworthy.

### Memory and the no-op AST copies

Peak RSS on this suite was 6.7 GiB for 62 MB of source — about 115x the
input — and roughly half of it came from two `SourceFile` clones taken
before checking whether they had anything to rewrite:

- `desugar_impl_for_test_in_file` clones, then rewrites tests carrying an
  `impl <Test> for <Tb>` binding.
- `normalize_vec_record_elem_fields` clones, then rewrites `Vec<Record, N>`
  field types.

Both now return `Cow` and borrow when the transform is a no-op.
ABBA-interleaved, 6 runs per arm, medians with observed ranges:

| | before | after |
|---|---|---|
| wall | 29.1 s (23.6-33.8) | **11.9 s** (10.9-12.8) |
| peak RSS | 6866 MiB (6859-6866) | **3250 MiB** (3239-3252) |
| lower | 11.1 s (4.1-12.6) | 2.35 s (2.0-3.3) |
| split plan | 10.1 s (8.3-10.9) | 0.55 s (0.5-0.8) |

Peak RSS reproduces to within 0.2% run to run, so it can be read at face
value; the wall figures are from a shared host and only the interleaved
comparison means anything.

**This suite is the best case, not the typical one.** `gen_suite.py`
emits classic-form tests, so both transforms borrow throughout. 166 of
this repo's 185 fixtures use `impl <Test> for <Tb>`, and for those the
TB-IR path still takes the desugar clone three times over: `lower_program`
desugars into a local binding that dies when it returns, and `cmd_sim`
passes the original merged file to `dut_probes`, to lowering, and to the
randomize emitter. Desugaring once in `cmd_sim` would collapse all three
to a borrow and is the obvious follow-up; it is a pipeline change rather
than a local one, so it is not in this measurement.

Split planning being ~10 s was previously read as its solver work, which
is what the name suggests. It was mostly these copies — the scaffold build
itself is ~0.5 s.

What remains is mostly live data: the AST and the lowered `TbProgram`,
resident together because shard emission needs the source file. A
parse-only `harc check` on this suite peaks at 2.9 GiB, which bounds the
AST's own footprint. Going lower means changing its representation.

### Shrinking the AST nodes

Two representation changes, both of which cost one `Box` or one integer
cast and nothing else:

- `Span` holds `u32` offsets instead of `usize`. A span is embedded in
  nearly every node, so halving it takes `Expr` from 24 bytes to 16 —
  and expressions are the most numerous nodes in the tree by a wide
  margin. The 4 GiB-per-file cap is far above what the parser could hold
  in memory anyway.
- `StmtKind::Let` is boxed. `LetStmt` carries an `Ident`, an
  `Option<TypeExpr>` and two `Vec`s, and an enum is as large as its
  largest variant, so inline it forced *every* statement to the size of a
  `let`.

| | before | after |
|---|---|---|
| `Stmt` | 240 B | **120 B** |
| `ExprKind` (heap-allocated per `Expr`) | 120 B | **96 B** |
| `Expr` | 24 B | **16 B** |
| `TypeExpr` | 88 B | **72 B** |
| `Ident` / `Path` | 40 B | **32 B** |

ABBA-interleaved on the split-emit run above, 6 runs per arm (medians,
observed ranges; the first run of each session is discarded as cold):

| | before | after |
|---|---|---|
| peak RSS | 3251 MiB (3251-3252) | **2811 MiB** (2810-2811) |
| parse | 3.5 s (3.3-4.3) | **2.4 s** (2.4-2.7) |
| wall | 13.0 s (12.6-13.8) | **11.9 s** (10.6-12.3) |
| lower | 3.4 s (3.1-3.6) | 3.5 s (2.6-3.6) — no change |

Parse-only `harc check` on the same suite: 2938 MiB → **2368 MiB**, a
19% cut, which is where the saving actually lives — lowering is
unaffected, and the emit phase never sees these types. Generated bytes
are identical: all 185 fixtures produce identical `dump-ir` and identical
`harc check` diagnostics, 330 fixture/codegen combinations emit identical
C++, and the 348 MB split output above is byte-for-byte unchanged.

The next-fattest `StmtKind` variant is now `If` at 112 bytes, but `if` is
common enough that boxing it trades an allocation per statement for 8
bytes per statement — a worse deal than either change above. Beyond that
the remaining lever is string interning: `Ident` is 32 bytes because it
owns a `String`, and roughly half of all instructions still go to
malloc/free.

What this measurement establishes:

1. **Shard I/O was the Amdahl ceiling on `--emit-jobs`, and it is gone.**
   The remaining sublinearity at 4 workers is the host having exactly 4
   cores.
2. **Parse and lower are the two largest printed phases, and they are
   now comparable.** Emission is under a second and split planning is
   about half a second; parse and lower are a few seconds each — parse
   led until the AST shrink above, which cut it by about a third and left
   lowering slightly ahead. The unprinted startup/teardown residual is
   comparable to either, so "long pole" would overstate both. Split
   planning used to be the largest phase at ~11 s
   — it builds the suite-global scaffold every shard reuses — but almost
   all of that turned out to be the no-op AST copies described above, not
   the solver work its name suggests.

3. **Two whole-AST deep copies used to sit in that path** — `merge_for_sim`
   cloning every item out of the parsed files, and a `merged.clone()` for
   suite-scope codegen. Removing them cut wall time by roughly a third and
   peak RSS by about a third as well (10.2 GiB → 6.7 GiB on this suite,
   ABBA-interleaved), because `merged` and its clone were both resident for
   the whole of lowering. `merge` itself went from ~2 s to ~0.1 s.

   Measured, ABBA-interleaved: lowering roughly halved. Parse did
   *not* change — an early non-interleaved measurement suggested it had,
   but parse runs before either removed copy is ever allocated, so there
   is no mechanism for it, and interleaved runs show only noise. That
   mistake is recorded here rather than quietly dropped, because it is the
   second time non-interleaved timings on this host produced a plausible
   but wrong number.

   A callgrind profile still attributes roughly half of all instructions
   to malloc/free traffic, so string interning or arena allocation in the
   AST is the next lever.

Note this synthetic is far cheaper per byte than the production suite in
harc#538, which measured ~23 minutes for ~1.2 GB using the *legacy v1*
emitter. TB-IR emits hundreds of MB/s on this host, so the two are not
directly comparable — the production suite cannot yet lower through TB-IR
(a passive composite-component gap, since fixed), which is the reason this
benchmark exists.
