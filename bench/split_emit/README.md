# split-emit benchmark

Measures TB-IR split C++ emission (`--codegen tbir --cpp-split tests`) —
the frontend phase that harc#538 targets. Everything here runs under
`--emit-only`, so no Verilator is required.

```sh
cargo build --release
bench/split_emit/run_bench.sh                 # defaults: 352 tests, group 32, 3 reps
bench/split_emit/run_bench.sh /tmp/bench 16 5 # custom workdir / group size / reps
```

`gen_suite.py` writes a synthetic suite plus a trivial DUT. The production
suite that motivated the issue is proprietary and does not lower through
TB-IR yet (a passive composite-component gap, tracked separately), so the
generator reproduces the shape that matters instead: a double-digit shard
count, test bodies big enough that emitting a shard is real work, and
suite-global scaffolding (constrained transaction records plus a
`randomize` site per test) that exercises the solver problem table and
randomize snippets reused across shards.

Not wired into CI — it takes minutes and writes hundreds of MB.

## What to read

`harc` prints each frontend phase, so a slow run can be attributed
without reaching for a profiler:

```
TBIR parse: 6.1s | merge: 0.1s
TBIR lower: 10.9s | verify: 0.4s
TBIR split plan: 352 tests, 11 shards, group size 32, emit jobs 4, planned in 10.8s
TBIR shard 3/11: 32 tests, 31.7 MB, 0.3s, emitted
TBIR split emit: 11/11 shards, 348.6 MB, 0.7s
```

These cover everything between reading the sources and the last shard
hitting disk. What they do *not* cover is process teardown — dropping the
AST and the lowered program at exit was measured at ~6 s on this suite —
so the printed phases will sum to less than the wall clock.

The final rerun in the script re-emits an unchanged suite. Every shard
then reports `reused`, so `write_if_changed` reads and compares but never
writes — the difference between that number and the clean-run emit time is
the write I/O.

## Reference measurement

4-core container, Linux 6.18, release build, 352 tests / 11 shards at
group size 32, 348.6 MB of generated C++.

Shard I/O runs on the worker that produced the shard. It used to run on a
single receiving thread, which serialized every shard's `write_if_changed`
— both the compare-read and the write — and put a ceiling on
`--emit-jobs`. Interleaved A/B against the previous implementation on a
shared 4-core host, 3-5 reps per cell, medians with observed ranges:

| jobs | I/O on receiver | I/O on worker |
|---|---|---|
| 1 | 2.0 s (1.8-2.1) | 1.9 s (1.7-2.1) |
| 2 | 1.3 s (1.2-1.4) | 1.1 s (1.1-1.2) |
| 4 | 1.2 s (1.1-1.2) | **0.7 s** (0.7-0.8) |

So ~1.7× on the emit phase at `--emit-jobs 4`, and speedup over serial
goes from ~1.7× to ~2.7×. Generated bytes are identical across every cell
and against the pre-change binary.

Treat the absolute seconds as soft: this host is shared and lowering
alone swung 8-13 s between runs. Only interleaved comparisons are
meaningful, and the ratios were stable across reps where the absolutes
were not. An earlier revision of this table reported 1.4 s for the
receiver-side `--emit-jobs 4` cell, which did not survive re-measurement —
non-interleaved timings on this host are not trustworthy.

What this measurement establishes:

1. **Shard I/O was the Amdahl ceiling on `--emit-jobs`, and it is gone.**
   The remaining sublinearity at 4 workers is the host having exactly 4
   cores.
2. **The frontend, not emission, is where the time goes.** Emission is
   under a second; parse, lower and split planning are each an order of
   magnitude larger. Split *planning* deserves particular attention — it
   builds the suite-global scaffold every shard reuses (solver problem
   table, randomize snippets, gated-bus check) and measures larger than
   parsing on this suite, which is not obvious from the name.

3. **Two whole-AST deep copies used to sit in that path** — `merge_for_sim`
   cloning every item out of the parsed files, and a `merged.clone()` for
   suite-scope codegen. Removing them cut wall time by roughly a third and
   peak RSS by about a third as well (10.2 GiB → 6.7 GiB on this suite,
   ABBA-interleaved), because `merged` and its clone were both resident for
   the whole of lowering. `merge` itself went from ~2 s to ~0.1 s.

   Measured, ABBA-interleaved: lowering roughly halved. Parse did
   *not* change — an early non-interleaved measurement suggested it had,
   but parse runs before either removed copy is ever allocated, so there
   is no mechanism for it, and interleaved runs show only noise. That
   mistake is recorded here rather than quietly dropped, because it is the
   second time non-interleaved timings on this host produced a plausible
   but wrong number.

   A callgrind profile still attributes roughly half of all instructions
   to malloc/free traffic, so string interning or arena allocation in the
   AST is the next lever.

Note this synthetic is far cheaper per byte than the production suite in
harc#538, which measured ~23 minutes for ~1.2 GB using the *legacy v1*
emitter. TB-IR emits hundreds of MB/s on this host, so the two are not
directly comparable — the production suite cannot yet lower through TB-IR
(a passive composite-component gap, since fixed), which is the reason this
benchmark exists.
