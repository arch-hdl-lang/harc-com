# split-emit benchmark

Measures TB-IR split C++ emission (`--codegen tbir --cpp-split tests`) —
the frontend phase that harc#538 targets. Everything here runs under
`--emit-only`, so no Verilator is required.

```sh
cargo build --release
bench/split_emit/run_bench.sh                 # defaults: 352 tests, group 32, 3 reps
bench/split_emit/run_bench.sh /tmp/bench 16 5 # custom workdir / group size / reps
```

`gen_suite.py` writes a synthetic suite plus a trivial DUT. The production
suite that motivated the issue is proprietary and does not lower through
TB-IR yet (a passive composite-component gap, tracked separately), so the
generator reproduces the shape that matters instead: a double-digit shard
count, test bodies big enough that emitting a shard is real work, and
suite-global scaffolding (constrained transaction records plus a
`randomize` site per test) that exercises the solver problem table and
randomize snippets reused across shards.

Not wired into CI — it takes minutes and writes hundreds of MB.

## What to read

`harc` prints the phases; the runner adds total wall time:

```
TBIR lower+verify: 35.4s
TBIR split plan: 352 tests, 11 shards, group size 32, emit jobs 4
TBIR shard 3/11: 32 tests, 31.7 MB, 0.6s, emitted
TBIR split emit: 11/11 shards, 348.6 MB, 1.7s
```

The final rerun in the script re-emits an unchanged suite. Every shard
then reports `reused`, so `write_if_changed` reads and compares but never
writes — the difference between that number and the clean-run emit time is
the write I/O, which is serialized on the receiving thread.

## Reference measurement

4-core container, Linux 6.18, release build, 352 tests / 11 shards at
group size 32, 348.6 MB of generated C++, 3 reps each (medians).

| configuration | emit phase | total wall |
|---|---|---|
| pre-#538 emitter (commit 4e39730) | — (not instrumented) | 78–111 s |
| `--emit-jobs 1` | 3.0 s | 48–69 s |
| `--emit-jobs 2` | 1.7 s (1.8×) | 47–53 s |
| `--emit-jobs 4` | 1.5 s (2.0×) | 48–54 s |
| `--emit-jobs 4`, unchanged rerun | 0.8 s (0.7–1.1) | — |

Generated bytes are identical across every row, verified with `diff -r`
against the pre-#538 binary as well as across job counts.

Three things this measurement establishes:

1. **Removing the per-shard `TbProgram` clone and hoisting the suite-global
   solver work is the dominant win** — roughly 2× total wall time at
   `--emit-jobs 1`, before any parallelism enters the picture.
2. **`--emit-jobs 4` reaches 2.0× on the emit phase here, short of the 2.5×
   target in harc#538 — and the contention is measurable rather than
   speculative.** The unchanged-rerun row isolates it: with nothing to
   write, the phase drops to 0.8 s, so roughly 0.7 s of every clean run is
   `write_if_changed` I/O for 348 MB, serialized on the receiving thread.
   The parallelizable remainder scales about 3× (≈2.3 s → ≈0.8 s); Amdahl's
   law on the serialized part caps the whole phase near 2×. This host also
   has exactly 4 cores to cover 4 workers plus the receiver, so `jobs=4`
   oversubscribes it.
3. **Emission is no longer the frontend's long pole.** Parse + lower is now
   ~16 s of a ~48 s run, against ~1.5 s for emission.

Next bottlenecks, in order: **write I/O** (parallelizing it, or writing
shards from the worker threads, would lift the ~2× ceiling), then **parse +
lower**. Neither is addressed here.

Note this synthetic is far cheaper per byte than the production suite in
harc#538, which measured ~23 minutes for ~1.2 GB using the *legacy v1*
emitter. TB-IR emits ~230 MB/s of C++ on this host, so the two are not
directly comparable — the production suite cannot yet lower through TB-IR
(a passive composite-component gap, tracked separately), which is the
reason this benchmark exists.
