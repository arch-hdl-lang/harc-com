# Design doc: Probing DUT-internal signals via SV `bind`

**Status:** Proposed (RFC, not yet implemented).
**Date logged:** 2026-05-13.
**Scope:** Add a `probe` field-kind to the testbench's `dut` declaration
so HARC source can observe signals deep inside a Verilator-compiled
SystemVerilog DUT without modifying the DUT source. Lowering is via SV
`bind` stubs + per-signal `/* verilator public */` marking.

## 1. Motivation

Spec §10.5 acknowledges the gap explicitly:

> No `internal` access to SV module internals beyond what Verilator's
> public accessors expose. Verilator can be coerced into exposing more
> via `/* verilator public */` annotations, but HARC v1 doesn't depend
> on this.
> No SVA on internal SV signals. HARC `assert` / `cover` / `assume` work
> fine on the DUT boundary signals; reaching internal SV signals for
> property checking requires Verilator hierarchical access (currently
> limited).

Three workarounds exist today (SV wrapper that re-exposes internals,
`/* verilator public */` on hand-edited SV source, hand-written `bind`
observer modules) — all require touching SV or wrapping the DUT. None
are HARC-native.

Common verification needs that depend on deep probing: pipeline-stall
counters, FSM-state coverage, FIFO-depth assertions, fault injection on
internal registers. Without first-class support, every team hand-rolls
the workaround and the test source ends up coupled to mangled Verilator
internals.

## 2. Goals and non-goals

**Goals:**

1. First-class `probe` declarations attached to the `dut` field inside a
   `testbench` block.
2. Read access syntax identical to top-level port access: `tb.dut.X`
   regardless of where in the hierarchy `X` actually lives.
3. Untouched DUT source. Probes lower to a separately-emitted `bind`
   stub, not modifications of the user's `.sv` files.
4. Compile-time path resolution. Bad probe paths fail the Verilator
   build (visible, early), not silently at sim start.
5. Optional force/deposit access for fault-injection use cases, opt-in
   per probe.

**Non-goals:**

1. Runtime path resolution / string-keyed lookups. The probe table is
   compile-time-known.
2. Generic hierarchical access (`tb.dut.<arbitrary>.<anything>`). Only
   declared probes are accessible. This keeps the interface auditable
   and the Verilator public surface minimal.
3. Probing inside ARCH-compiled DUTs. The ARCH path already supports
   typed hierarchical access (spec §10.5); `probe` is specifically for
   the Verilator-SV path.
4. Per-probe clock-domain crossing logic. Probes read the signal where
   it lives; CDC handling stays the user's responsibility.

## 3. Surface

```harc
testbench CpuTb
    let dut : Cpu
        probe flags  : uint<4>  at alu.flags
        probe pc     : uint<32> at fetch.pc
        probe stall  : bit      at pipeline.fsm.stall
        probe fifo_d : uint<5>  at rob.fifo.depth
        probe force ack_inject : bit at dcache.ack    // read/write opt-in
    end let dut

    bus : BusAxiLite = bind dut
    // ...
end testbench
```

### 3.1 Probe syntax

- `probe <name> : <type> at <dotted.path>` — read-only probe.
  - `<name>` is how the probe is accessed in HARC source.
  - `<type>` is the HARC type the codegen will surface.
  - `at <dotted.path>` is the hierarchical path inside the DUT, written
    as a HARC dotted token (no quotes for the common case).
- `probe force <name> : <type> at <dotted.path>` — read/write probe.
  The `force` keyword opts into Verilator's `$deposit`-equivalent
  write path. Required for fault-injection writes; reads behave the
  same as without `force`.
- `probe <name> : <type> at "<string-path>"` — string-form path. Escape
  hatch for paths that aren't valid HARC identifiers (e.g. names
  containing `[`, `]`, generate-block scopes). The recommended form is
  the dotted token; use strings only when the dotted form can't parse.

### 3.2 Access syntax

```harc
let s = tb.dut.stall          // read — identical to top-level port access
tb.dut.ack_inject = 1         // write (only valid when declared `probe force`)
```

The HARC type checker ensures:

- Read access works on any declared probe.
- Write access works only on `probe force` probes; assigning to a
  read-only probe is a HARC-level error pointing at the decl site.
- The HARC type matches the SV signal width at Verilator-compile time.
  A mismatch produces a Verilator error referencing both the HARC
  probe decl line and the SV signal.

## 4. Lowering

### 4.1 SV `bind` stub generation

For the `Cpu` example above, HARC emits a stub `.sv` file alongside the
generated testbench `.cpp`:

```sv
// Generated by harc — do not edit.
// Probes for testbench CpuTb : dut : Cpu

module __harc_probe_Cpu;
    /* verilator public */ logic [3:0]  flags;
    /* verilator public */ logic [31:0] pc;
    /* verilator public */ logic        stall;
    /* verilator public */ logic [4:0]  fifo_d;
    /* verilator public */ logic        ack_inject;

    assign flags      = alu.flags;
    assign pc         = fetch.pc;
    assign stall      = pipeline.fsm.stall;
    assign fifo_d     = rob.fifo.depth;
    assign ack_inject = dcache.ack;
endmodule

bind Cpu __harc_probe_Cpu __harc_probes ();
```

Notes on the SV pattern:

- The bound module sits **inside every instance of `Cpu`** in the
  hierarchy. The `assign` upward references resolve relative to that
  scope, so `alu.flags` means `<containing Cpu>.alu.flags` — no global
  `$root` path needed.
- `/* verilator public */` is applied **per signal**, not via the
  global `--public-flat-rw` flag. This keeps Verilator's optimizer
  free to remove every non-probed signal as usual.
- The stub is fully generated and overwrites on each build. Users
  never edit it.

For `probe force` probes, the lowering uses `logic` (writable) instead
of `wire`, and the stub additionally emits a write-back assign:

```sv
/* verilator public */ logic ack_inject_drive;
/* verilator public */ logic ack_inject_drive_en;
always_comb begin
    if (ack_inject_drive_en)
        force dcache.ack = ack_inject_drive;
    else
        release dcache.ack;
end
```

(SV `force` / `release` semantics. Cost: forces gate-level optimization
of the target signal, hence opt-in.)

### 4.2 Verilator build invocation

The HARC sim runner passes the stub `.sv` to Verilator alongside the
user's DUT source:

```sh
verilator --cc --exe --build \
    user_dut.sv \
    __harc_probe_Cpu.sv \
    harc_tb.cpp \
    --top-module Cpu \
    ...
```

No global `--public-flat-rw`; only the per-signal annotations expose
what the testbench actually probes.

### 4.3 HARC signal-access codegen

For each probe, HARC stores in the testbench AST: `{name, type, path,
mangled_accessor}`. When HARC codegen encounters `tb.dut.stall`, it
looks up `stall` in the probe table for `tb.dut`'s type (`Cpu`) and
emits the Verilator-mangled accessor:

```cpp
// tb.dut.stall lowers to:
dut->__harc_probes->stall
```

(Exact mangling form depends on Verilator version; codegen formats it
from the probe metadata at emit time.)

`probe force` writes lower to setting the `_drive` + `_drive_en` pair.

### 4.4 Path resolution time

The dotted path `at alu.flags` is parsed by HARC into a path token and
written verbatim into the generated `.sv` stub. **HARC does not
validate that the path exists in the DUT.** Validation happens at the
Verilator compile step: if `alu.flags` doesn't resolve, Verilator
errors with a message that names the stub line and the bad reference.

This is intentional — HARC doesn't have a parser for the DUT's SV
source, and adding one to type-check probe paths is out of scope.
Verilator already does this work; HARC defers to it and surfaces the
error.

## 5. Diagnostics

When a probe path doesn't resolve, the user sees:

```
verilator: __harc_probe_Cpu.sv:8: error: can't find 'flags' in 'alu'
note: probe declared in CpuTb at line 4
   probe flags : uint<4> at alu.flags
                            ^^^^^^^^^
```

The "note" line is emitted by the HARC build runner, which parses
Verilator's stderr and cross-references stub line numbers to the
originating probe decl. Without the cross-reference, the user sees only
the mangled stub name and is left guessing — so this is a load-bearing
part of the UX, not optional.

## 6. Migration / new-feature only

`probe` is new syntax. No existing code changes; testbenches that don't
declare probes generate no stub `.sv` and trigger no Verilator public
exposure. Zero impact on the current 76 fixtures.

## 7. Open questions

### 7.1 Multiple `Cpu` instances

If the DUT contains two instances of `Cpu` (e.g. dual-core), the `bind
Cpu __harc_probe_Cpu` directive instantiates the stub inside **both**.
Each instance gets its own probe values. HARC's `tb.dut` refers to the
top-level Cpu instance only — multi-instance probing isn't supported
in v0.1.

**Resolution:** error at the testbench decl if the DUT has more than
one instance of a probed module type, with the suggestion to use a
qualified path (`at /core0/alu.flags`) once that's designed. Defer the
multi-instance design.

### 7.2 Probing modules vs probing signals

The current design only probes signals (leaf values). Users may want to
probe a struct-typed bus or an aggregate (`probe axi_internal :
BusAxi4`). This requires HARC to know the SV-side struct layout, which
opens the typed-protocol question already deferred to v1.1 per spec
§10.5. Park until convention-based grouping lands.

### 7.3 Force-release granularity

`probe force` declares a force-capable probe, but the actual force is
exercised by writing the probe name. Should there be an explicit
`force` / `release` operator (parallel to SV) or is plain assignment
plus an `= z` (release) sufficient? Plain assignment is simpler;
release-by-Z is non-standard. Recommend an explicit `release tb.dut.X`
statement; defer the exact syntax to first user need.

### 7.4 Coverage and assertions on probes

Probes are ordinary HARC fields once declared, so existing `assert` /
`cover` / `covergroup` syntax should work against them without
additional design. Worth a spec sentence to confirm; no implementation
work.

## 8. Scope of v0.1 implementation

1. Parser: `probe` and `probe force` declarations inside
   `let dut : T ... end let dut` in `testbench` blocks.
2. AST: probe table on the testbench-owned DUT field, threaded through
   to codegen and `impl <Test> for <Tb>` desugaring.
3. SV stub emitter: emits `__harc_probe_<DutType>.sv` next to the
   generated `.cpp`.
4. HARC signal-access lookup: extends the `dut.X` resolution path to
   consult the probe table.
5. Verilator runner: adds the stub to the Verilator command line.
6. Diagnostic shim: cross-references Verilator stderr to probe decl
   sites.
7. One fixture exercising read-only probes against `tests/dut/cpu_pipeline.sv`
   (or similar existing DUT with internal state worth observing).

`probe force` (§4.1 force/release) is scoped for v0.2 — gates on first
user request for fault injection.
